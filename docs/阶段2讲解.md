## 原来的请求流程如何变化

阶段 1：JSON → 启动时读入内存 → 接口返回。

阶段 2：JSON → 一次性导入 MySQL → 每次接口请求建立 Session → 查询 MySQL → 返回 JSON。

应用启动时只检查数据库连接，不自动建表或导入，避免每次启动悄悄改变数据。
运行中的 API 不再读取 JSON，因此导入后修改 JSON 不会直接改变接口结果；需要在数据库里修改数据。

- config.py：读取本地连接配置，用 URL.create 处理密码中的特殊字符。
- database.py：建立连接池，给每次请求提供 Session，请求结束关闭 Session。
- models.py：将 Python 类对应到数据库表。
- repository.py：通过 SQLAlchemy 查询表，把结果转换为 API 数据结构。
- migrations：明确记录第一次建表操作，便于其他电脑复现。
- seed_demo.py：在一个事务中写入地点与道路；失败则回滚。

SQLAlchemy 是 Python 操作数据库的工具；PyMySQL 是连接 MySQL 的驱动；Alembic 管理表结构版本。MySQL 才是真正保存数据的服务。

## 两张业务表

| 表 | 保存什么 | 关键约束 |
| --- | --- | --- |
| attractions | 地点编号、代码、名称、介绍、坐标、验证状态 | 编号主键；code 唯一；坐标范围 |
| roads | 起终点、距离、双向标记、验证状态 | 端点外键；距离为正；起点编号小于终点；端点组合唯一 |

道路统一将较小编号作为 start_id，避免 A→B、B→A 重复存储。同一条记录代表双向道路，不代表只允许小编号走向大编号。
当前模型只面向 demo 数据，地点状态限制为 demo_only；真实校园图的入口节点与交叉口模型在后续真实数据阶段再调整。
