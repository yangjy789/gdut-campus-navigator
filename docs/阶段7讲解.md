# 阶段 7：AI 工具调用规划路线

## 本次完成

校园知识助手新增「AI 规划路线」模式：用一句话说出起点和终点，助手识别地点后由后端 Dijkstra 在示例道路上真实计算最短路线，并在地图上高亮。
2026-11-23 已完成真实验收，见 [stage-7-check.json](stage-7-check.json)，状态 `passed`。后端 84 项测试通过，前端构建通过。

必须先说明：本阶段只把「地点识别」交给模型，**路线和距离一律由后端算法计算**。模型不返回距离、坐标、编号或路线描述，也没有能力编造路线。

## 工具调用（function calling）的流程

用户问题 → 模型用 plan_route 工具只抽取起点/终点地点短语 → 后端对照真实地点表解析编号 → 检查是否有歧义或同点 → 调用已有 plan_route（Dijkstra）算真实路线 → 前端高亮地图并显示结果。

这叫工具调用：模型决定「用户想去哪」，程序负责「怎么走、走多远」。模型只产出结构化参数，所有关键计算都留在可测试、可核对的后端代码里。

## 为什么不让模型直接给路线

- 模型不知道本项目的真实道路图和距离，直接回答必然编造。
- 让模型只填地点名称，再用本地地点表解析，可以把「火星基地」这类不存在的地点挡住。
- 「教学楼」同时匹配教学楼 A 和教学楼 B，属于歧义，必须要求用户说清楚，不能替用户猜。
- 距离、路径、分段全部来自 Dijkstra 结果，可对账：分段距离之和等于总距离。

## 地点解析

后端新增 `backend/app/place_resolver.py`，中文别名与前端 demo-layout.ts 的 labels 保持一致（北门、图书馆、食堂、教学楼 A/B、宿舍区……）。管理员若把地点改成非示例名称，以新名称匹配；原始英文示例名仅在仍是示例名时匹配。解析规则：精确匹配优先；模糊匹配只在唯一命中时接受，多个命中视为歧义并返回 None。

## 接口

- POST /api/assistant/route ，请求体 `{"question":"从北门到食堂怎么走"}`，返回 status 为 planned / need_clarification / no_route。planned 时 route 字段与 /api/routes/shortest 结构一致，可直接交给地图高亮。
- GET /api/assistant/route/status ，查看服务商、型号、工具名与配置状态。

限速与知识助手一致：每个客户端每分钟最多 10 次，同时最多 1 个模型请求；429 不自动重试，503 最多 3 次间隔重试并共用 50 秒时间预算。密钥不进入浏览器，模型只收到问题和工具定义。

## 如何使用与验收

1. 打开 http://127.0.0.1:5173/ ，向下找到「校园知识助手」，切换到「AI 规划路线」。
2. 点击「从北门到食堂怎么走」发送，应显示 290 米、路径 NG → LIB → SC → DIN，地图同步高亮。
3. 输入「从图书馆去运动场」，应显示 330 米。
4. 输入「从教学楼到食堂」，应提示地点有歧义并要求说清楚；输入「从火星基地到食堂」应提示无法确认地点。两者都不应返回路线。
5. 「清除地图高亮」按钮可取消高亮；左侧手动表单与 AI 规划互相同步。

自动验收命令：

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
.\.venv\Scripts\python.exe -m scripts.check_route_assistant
```

自动测试只替换模型响应，不消耗模型额度；真实请求单独检查并记录在 stage-7-check.json。

## 已知限制

- 地点别名仅覆盖 12 个课程示例地点；真实校园数据核验后需要补充别名表。
- 模型只有「抽取地点」这一步，不做多轮对话、不记忆上下文。
- 中文地点识别依赖模型理解能力；生僻说法可能识别失败，此时请用左侧手动表单。
- 路线仍是课程示例，不能用于真实导航；阶段 8 完成部署后仍需等真实数据核验才能发布真实导航。
